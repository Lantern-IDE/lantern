# 에이전트 부검: `lantern check`와 `lantern autopsy`

코딩 에이전트가 "끝났습니다"라고 말한 뒤, 디스크에 이미 남아 있는 세션 로그와 코드 그래프로 무엇을 빠뜨렸는지 확인하는 명령입니다. API 키도, 모델 호출도, 네트워크도 쓰지 않습니다.

## 먼저 읽을 결론

**재 보니 에이전트가 진짜로 놓친 호출부는 드물었습니다.** 만들 때는 "놓친 호출부를 잡아 준다"를 앞세우려 했지만, 작성자 본인의 세션에서 읽어 판정한 경고 30건 중 진짜 놓침은 0건이었습니다. 이 데이터로는 그 문구를 쓸 수 없어서 쓰지 않습니다. 다만 한 사람의 세션이고 수가 적어서, 다른 사람이나 다른 모델에서도 그렇다고 말할 수는 없습니다.

지금 근거를 갖고 말할 수 있는 것은 이렇습니다.

- **지운 이름의 참조(Dangling)는 맞는 쪽을 가리켰습니다.** 공개 커밋에서 경고 5건 중 4건이 그 커밋이 실제로 고친 파일이었습니다. 5건은 정밀도라고 부르기에 너무 적습니다.
- **조용합니다.** 공개 커밋 71개 중 9개에서만 경고가 나왔고, 기본 출력에는 Dangling만 나옵니다.
- **테스트를 안 돌렸을 수 있는 구간을 셉니다.** 작성자 세션에서는 관련 테스트가 있는 작업 구간 64개 중 최대 13개였습니다. 명령 모양으로 알아보므로 상한으로만 읽어야 합니다.
- **아무것도 막지 않습니다.** 미리 정한 정밀도 기준을 어느 종류도 넘지 못해, Stop 훅은 개수만 남기고 에이전트를 세우지 않습니다.

## 무엇을 하나

| 명령 | 하는 일 | 기본 출력 |
|---|---|---|
| `lantern check [--base HEAD]` | 작업 트리를 기준 커밋과 비교해, 지운 이름과 바뀐 시그니처가 손대지 않은 파일에 남았는지 봅니다 | Dangling만. `--details`로 Stale caller까지, `--all`로 20개 상한 없이. `--json`에는 Stale caller도 들어갑니다 |
| `lantern autopsy [--days 30] [--max-sessions 40]` | 지난 세션을 하나씩 되짚어 같은 검사를 그때의 코드에 돌리고 git 이력으로 확인합니다 | 한 화면. `--details`로 전부, `--json`은 전부 |
| `lantern hook install claude` | Claude Code Stop 훅을 넣습니다. 에이전트를 막지 않고 개수를 기록합니다. `lantern check --stats`로 봅니다. 무엇이 디스크에 남는지는 [개인정보](#개인정보)에 적었습니다 | 바뀐 설정과 그 설명 |

찾는 것은 두 가지입니다.

- **Dangling**: 지운(또는 이름을 바꾼) 심볼의 참조가 손대지 않은 파일에 남아 있고, 같은 언어 계열에 그 이름의 정의가 더 없습니다.
- **Stale caller**: 시그니처가 바뀐 심볼의 호출이 손대지도 읽지도 않은 파일에 남아 있습니다. 같은 이름이 남아도 오버로드가 사라져 그 인자를 받을 정의가 없으면 여기에 듭니다. 본문만 바뀐 것은 보고하지 않습니다.

## 어떻게 찾나

1. **심볼 변화.** 편집 전후 본문을 tree-sitter로 파싱해 이름과 종류로 맞춥니다. 공백, 주석, 공개 범위만 바뀐 것과 원래 호출이 그대로 되는 변화는 빼고 봅니다. 끝에 선택 매개변수 추가, 기본값 추가, Java 오토박싱, TypeScript 매개변수 유니온 넓히기, Kotlin 기본값 삽입(그 뒤가 모두 기본값일 때), Kotlin null 허용으로 넓히기가 그런 변화입니다.
2. **이름으로 참조 찾기.** 옛 이름을 코드 그래프에서 찾습니다. 3글자 미만이거나 흔한 이름(`get`, `run` 등), 정의가 6개 이상인 이름은 건너뜁니다.
3. **이름만 같은 것 거르기.** 틀린 경고는 대부분 같은 이름의 다른 메서드였습니다. 그래서 메서드와 함수는 다음 중 하나가 있어야 참조로 칩니다.
   - 참조 파일이 정의 파일 이름을 부릅니다 (`index`, `mod`, `__init__`은 폴더 이름)
   - 참조 파일이 메서드를 감싼 타입 이름을 부릅니다
   - 같은 패키지입니다 (Go, Kotlin)
   - 패키지 이름을 붙여 부릅니다 (`flask.redirect`, `orders.Place`)
   - 그 이름을 가져오는 문장이 있습니다 (`import { x } from './a'`, `from a import x`, `use crate::x`)

   타입은 이름 자체가 근거라 이 조건을 보지 않습니다. C와 C++은 헤더로 이어져 파일 이름으로 판단할 수 없어 보지 않습니다. `private` 정의와 경로·이벤트로 프레임워크가 부르는 정의(`@GetMapping`, `[HttpGet]`, `@app.post`, `#[tauri::command]`)는 처음부터 뺍니다. `@Cacheable`처럼 표시만 붙은 평범한 메서드는 빼지 않습니다.
4. **이력으로 확인 (`autopsy`만).** 세션을 쉬는 시간 3시간 기준으로 작업 구간으로 나눕니다. 구간마다 첫 편집 직전 커밋을 임시 클론에 꺼내 그때의 인덱스로 검사합니다. 그 뒤 편집한 파일을 처음 건드린 커밋(14일 안, 없으면 지금 작업 트리)에서 확인합니다. 변경이 반영되지 않았으면 뺍니다. 그때 이미 참조가 고쳐졌거나 정의가 다시 생겼으면 뺍니다. 남은 경고는 그 뒤 14일 안에 **참조 줄 자체가 바뀌었을 때만** "그 줄이 바뀜"으로 표시합니다. 파일을 지운 것이나 감싼 함수의 다른 곳을 고친 것은 치지 않습니다.
5. **테스트.** 바뀐 심볼에 이어진 테스트가 있는데, 마지막 편집 뒤 테스트 명령이 로그에 없으면 그 구간을 셉니다.

## 잰 숫자

### 공개 커밋 (누구나 재현 가능)

[eval/check](../eval/check/README.md). 공개 저장소 10개, 언어 8종의 여러 파일 커밋 71개에서 고친 파일을 하나만 부모 커밋에 얹고 `lantern check`를 돌렸습니다. 고친 파일의 쌍은 182개입니다. Lantern `ea865cf`, 2026-11-02, Windows 11, 모델 없음.

| 방법 | 다른 정답 파일을 가리킨 커밋 | 커밋당 표시한 파일 (평균) | 표시한 파일 중 정답 밖 (잡음의 상한) |
|---|---|---|---|
| `lantern check` 전체 | 6 / 71 (8.5%) | 0.35 | 17 / 25 (68.0%) |
| Dangling만 (기본 출력) | 4 / 71 (5.6%) | 0.07 | 1 / 5 (20.0%) |
| Stale caller만 (`--details`) | 3 / 71 (4.2%) | 0.30 | 16 / 21 (76.2%) |
| 영향 반경 (`graph impact`) | 57 / 71 (80.3%) | 41.96 | 2849 / 2979 (95.6%) |
| 모든 심볼·참조·동시 변경 | 58 / 71 (81.7%) | 64.52 | 4443 / 4581 (97.0%) |

- 경고는 모두 63건입니다 (Dangling 5, Stale caller 58). 커밋당 평균 0.89건, 중앙값 0건이고, 48건이 테스트 파일에 있습니다.
- `check`는 대부분의 커밋에서 말이 없습니다. 71개 중 50개는 지운 심볼도 시그니처 변화도 없어 애초에 할 말이 없고, 나머지 21개 중 6개에서 맞췄습니다. 넓은 그물은 약 80%를 맞추지만 커밋당 42~65개 파일을 표시합니다.
- 경고가 정답 밖이라고 틀렸다는 뜻은 아닙니다. 그래서 잡음의 상한이라고 부릅니다. 이 표는 경고가 옳은지 판정하지 않습니다.
- 커밋 하나(gin)가 경고 35건을 냅니다. 전부 테스트 파일입니다. 이 경고들은 읽어 판정하지 않았습니다.

`--all --json` 기준입니다. `lantern check` 한 번은 중앙값 474.5 ms, 90번째 백분위 736 ms, 최대 3270 ms였고 152번 중 151번이 3초 안에 끝났습니다. 다른 빌드가 낮은 우선순위로 함께 돌던 PC라 대략으로 읽어야 합니다.

**조정이 공개 커밋에 미친 영향.** 조정 전 경고 65건에서 63건이 됐고, 정답을 가리킨 쌍 8개는 그대로입니다. 빠진 2건(okhttp, 테스트 파일)은 `promise.complete(...)`처럼 이름만 같은 다른 메서드를 짚은 것이었습니다. 처음 만든 규칙은 `import flask` 뒤의 `flask.redirect(...)` 3건도 뺐는데, 이것은 진짜 호출이어서 패키지 이름을 붙여 부르는 경우를 규칙에 넣었습니다. 그러므로 이 벤치마크는 규칙을 만들 때 완전히 숨겨진 자료가 아닙니다.

### 작성자 본인의 세션 (비공개, 합계만)

이 PC의 세션 로그를 읽었습니다. 코드나 이름은 저장소에 넣지 않았고 합계만 적습니다. **한 사람의 세션입니다. 일반화할 수 없습니다.**

|---|---|
| 기간 | 2026-07-02 ~ 2026-11-01 |
| Claude Code 세션 | 528개. 코드 편집 없음 465, 저장소가 지금 없음 45, **분석한 세션 18** |
| 저장소 / 작업 구간 | 32개 / 226개 |

사라진 저장소의 45개 세션에 코드 편집의 49%(4,064건)가 있었으니, 분석한 18개가 전체를 대표한다고 볼 수 없습니다.

**조정 전 경고의 판정.** 판정 기준은 데이터를 보기 전에 정했습니다. 진짜(REAL)는 같은 선언을 가리키고 그 시점 호출이 깨지는 것, 볼 만함(WORTH)은 돌아가지만 의미가 바뀐 것, 무해(HARMLESS)는 같은 선언이고 호환되는 변경, 틀림(WRONG)은 다른 선언이거나 호출이 아닌 것입니다.

| 종류 | 발견 | 표본 | 진짜 | 볼 만함 | 무해 | 틀림 | 진짜+볼 만함 | 기준 | 결과 |
|---|---|---|---|---|---|---|---|---|---|
| Dangling | 0 | 0 | - | - | - | - | 잴 수 없음 | 70% | 넘지 못함: 보이지만 막지 않음 |
| Stale caller | 68 | 30 | 0 | 0 | 3 | 27 | 0% (95% 상한 약 11%) | 60% | 넘지 못함: `--details`에서만, 막지 않음 |

- 발견 68건은 심볼 변화 10개에 몰려 있습니다. 심볼 단위로 보면 95% 상한은 약 28%입니다.
- Dangling은 이력 확인 전에 30건이 있었고 모두 빠졌습니다. 25건은 패키지를 옮긴 것이고, 5건은 정의나 참조가 남지 않은 것입니다. 읽어 보니 빠진 것이 옳았습니다.
- 세션 뒤에 바뀐 호출(later_fixed) 2건도 진짜가 아니었습니다. 같은 이름의 다른 메서드였고 1건은 파일 삭제를 고침으로 센 것이었습니다. 지금은 참조 줄이 바뀔 때만 셉니다.

**놓침은 얼마나 드문가.** 바깥 참조가 있는 파괴적 변경 226건 중 180건은 참조 파일을 모두 함께 고쳤습니다. 그중 14건을 읽었고 어긋난 호출은 없었습니다. 남은 46건에서 읽은 표본에도 진짜가 없었습니다. 226건을 모두 읽은 것이 아니어서 변경당 놓침의 상한은 계산하지 않습니다. 흔한 이름이거나 정의가 6개 이상이라 보지 못한 변경 249건은 여기에 들지 않습니다. 놓친 것을 독립적으로 찾아 본 것은 아니어서 회수율은 증명하지 못했습니다.

**조정 뒤.** 위 판정을 바탕으로 "어떻게 찾나"의 규칙을 넣고 같은 저장소에 다시 돌렸습니다. 재현을 빼고 같은 옵션(`--all --deep --max-seconds 300`)입니다. 저장소 32개 모두 정상 종료했고, HEAD, 상태, 인덱스, 설정이 바뀐 저장소는 없습니다. 작업 구간은 그사이 쌓인 로그 때문에 227개가 됐습니다.

| | 조정 전 | 조정 뒤 |
|---|---|---|
| Dangling | 0 | 0 |
| Stale caller | 68 | 1 |
| 이력 확인 전 원시 발견 | 252 | 42 |
| 표본 30건 중 여전히 나오는 것 | | 1건 (무해로 판정한 것) |
| 관련 테스트가 있는 구간 중 테스트 명령이 안 보이는 구간 | 64개 중 35개 | 64개 중 13개 |

- 표본의 진짜 발견이 0건이어서 "진짜를 잃지 않았다"는 확인은 뜻이 없습니다. 대신 빠지는 참조 쪽을 24건 뽑아 읽었고 진짜 호출은 0건이었습니다(95% 상한 약 12%). 규칙 대부분은 Java 위주인 이 자료에서 왔습니다(발견 68건 중 66건이 Java). 다른 언어에서는 공개 커밋 말고는 확인이 적습니다.
- 남은 1건은 제네릭 안의 유니온을 넓힌 변경입니다(`Ref<A | null>` → `Ref<A | B | null>`). 무해로 판정했지만, 제네릭 안쪽이 호환되는지는 타입을 봐야 알 수 있어 규칙을 더 넓히지 않았습니다.
- 경고가 0건에 가까워진 것은 도구가 좋아졌다는 뜻이 아니라, 이 자료에서는 알릴 것이 없다는 뜻입니다.
- 테스트 수가 줄어든 것은 에이전트가 달라져서가 아니라 `gradlew build`, `:모듈:test`, `pnpm check`, `flutter.bat`, `manage.py test`를 이제 알아보기 때문입니다. 남은 13구간 중 4구간이 한 세션입니다. 이 13구간은 읽어 판정하지 않았고, 아직 못 알아보는 명령이 있을 수 있어 상한입니다. 비율로 일반화하지 마세요.

**믿을 수 없어서 내보내지 않는 숫자.** 세션의 첫 질문으로 맥락을 조립해 편집한 파일이 앞 3개에 드는지 보는 재현은 33회 중 19회(58%)였는데, 무작위로 3파일을 골랐을 때의 기대치가 약 67%였습니다. 그래서 기본으로 돌리지 않고 글 보고서에 넣지 않습니다. `--replay`를 주면 JSON에만 나옵니다.

**파싱 확인.** 실행당 약 58만 줄 중 알아보지 못한 줄이 10줄, 형식 경고 0건입니다. 독립 집계와 비교해 놓친 세션이 없었고, 확인한 세션 1개의 토큰이 정확히 맞았습니다.

**토큰과 비용.** 세션 전체 값입니다. 한 세션이 여러 저장소를 만지면 저장소마다 전부 더해지므로, 저장소별 값을 더하면 부풉니다. 도구 호출은 이 저장소만 세므로 호출 0번에 토큰이 많게 나올 수 있습니다. 비용은 2026-11-02 정가표로 계산한 추정이고 실제 청구액이 아닙니다. 가격표에 없는 모델은 짐작하지 않습니다.

## 못 보는 것

- 이름 기반입니다. 동적 디스패치, 의존성 주입, 이름 충돌을 풀지 못합니다. 모든 경고는 "그럴 수 있다"입니다.
- 참조 파일이 정의 파일이나 타입 이름을 부르지 않으면 잇지 않습니다. 타입 추론으로 받은 객체의 메서드 호출(`getService().place()`)을 놓칠 수 있습니다.
- 경로로 부르는 엔드포인트를 테스트에서 직접 부르는 호출을 놓칩니다.
- 시그니처가 그대로면 의미가 바뀌어도 모릅니다.
- 셸로 읽은 파일은 모릅니다. Codex는 읽은 파일을 알 수 없어 "읽지 않았다"고 말하지 않습니다.
- 흔한 이름과 정의가 6개 이상인 이름은 보지 않습니다.
- 1MB가 넘거나 바이너리이거나 읽지 못한 파일은 비교하지 않습니다. `lantern check`는 그런 파일이 몇 개인지 알려 줍니다. 그래서 경고가 없다는 말은 "찾지 못했다"이지 "없다"가 아닙니다.
- 일부만 받은 클론(`--filter=blob:none` 등)에서 빠진 본문을 받으러 나가지 않습니다. 그 파일은 비교하지 못한 파일로 셉니다. `GIT_NO_LAZY_FETCH`를 모르는 오래된 git에서는 이 보호가 듣지 않습니다.
- 커밋하지 않고 사라진 저장소의 세션은 분석할 수 없습니다.

## 실행 조건

- Windows에서 시험했습니다. 경로는 대소문자를 가리지 않고 `/`로 맞춰 비교합니다. macOS와 Linux는 시험하지 않았습니다.
- 파서는 Rust, Python, TypeScript/JavaScript, Java, Kotlin, Go, C#, C/C++를 읽습니다.
- `autopsy`의 `--max-seconds`(기본 120초)는 세션 분석을 끊습니다. 로그 읽기는 끊지 않습니다. `--deep`으로 모든 프로젝트 폴더를 읽으면 로그 읽기에 시간이 가장 많이 들고(앞선 실행에서 77%), 상한을 넘을 수 있습니다.
- Stop 훅은 2초 예산 안에 못 끝내면 그냥 지나가고, 어떤 오류든 출력 없이 종료 코드 0으로 끝납니다.
- 다른 프로세스가 인덱스를 쓰고 있으면 `lantern check`는 5초, Stop 훅은 0.5초 기다린 뒤 마지막으로 저장된 인덱스로 봅니다. 글 출력과 `--json`의 `index_stale`로 알려 줍니다.

## 개인정보

- 저장소를 바꾸지 않습니다. `autopsy`는 임시 폴더의 클론과 인덱스만 쓰고 끝나면 지웁니다. Ctrl+C로 끊어도 지우고 종료 코드 130으로 끝납니다. 강제 종료나 정전처럼 정리할 틈이 없으면 남고, 다음 `autopsy`가 하루 지난 것을 지웁니다. 측정한 저장소 32개에서 HEAD, 상태, 인덱스, 설정이 그대로인지 실행마다 확인했습니다.
- 모델을 부르지 않고 네트워크를 쓰지 않습니다.
- `~/.claude/projects`와 `~/.codex/sessions`를 읽습니다. 메시지, 명령은 출력하지도 저장하지도 않습니다. 첫 질문은 `--replay`일 때 메모리에서만 쓰고 버립니다.
- 출력과 `--json`에는 경로와 심볼 이름, 세션 ID가 들어갑니다. 내 PC에서 보는 용도입니다. 밖에 붙이기 전에 확인하세요.
- 데이터 폴더(`LANTERN_DATA_DIR`, 기본은 OS의 앱 데이터 폴더 아래 `lantern`)에 남는 것은 다음과 같습니다.
  - `check-log.jsonl`과 세션 상태 파일: 개수와 해시만.
  - `index/`: `lantern check`와 Stop 훅이 쓰는 인덱스. 심볼 이름, 파일 경로, 줄 번호, 파일 해시만 있고 코드, 시그니처, 주석은 없습니다. `lantern hook uninstall claude`가 이 저장소의 것을, `--user`를 붙이면 전부를 지웁니다.
  - `settings-backups/`: 훅을 넣고 뺄 때 만드는 설정 파일 백업. 설정에 토큰이 있으면 백업에도 있습니다. 저장소 안에 두면 커밋될 수 있어 여기에 둡니다. 자동으로 지우지 않습니다.
- 저장소에 이미 `.lantern/index.db`가 있거나 `LANTERN_INDEX_DIR`을 정했으면 그 인덱스를 씁니다. 이것은 검색을 위해 사용자가 만든 전체 인덱스라 코드 조각이 들어 있습니다.

## 기준을 다시 보는 조건

어느 종류든 다른 사람의 세션에서 같은 방식으로 표본을 읽어 기준을 넘기면, 그때 `BlockPolicy::MEASURED`를 바꿉니다. 그 전에는 막지 않습니다. "놓친 호출부" 문구도 그때 다시 정합니다.

## 재현

```bash
cargo build --release -p lantern-context
./target/release/lantern -C <저장소> check --details
./target/release/lantern -C <저장소> autopsy --all --deep --details
node eval/check/run.mjs --dir <클론 폴더>     # 공개 커밋 측정
```
