# 차별화: 작업과 지도

## 1. 왜 바꾸나

에이전트에게 코드를 맡기는 일이 늘수록, 개발자에게 필요한 것은 "코드를 치는 화면"보다 **"에이전트가 무엇을 보고 무엇을 바꿨고, 그게 어디까지 닿는지 확인하는 화면"**이다.

| 도구 | 중심 | 에이전트 작업을 확인하는 방법 |
|---|---|---|
| VS Code | 파일 트리 + 편집기 | 확장(Copilot 채팅)의 대화 기록 |
| Cursor, Windsurf | VS Code 구조 + AI 채팅·에이전트 패널 | 대화 기록, 파일별 Diff |
| Orca | 여러 에이전트를 병렬로 (작업 공간 분리) | 에이전트별 터미널·Diff |
| **Lantern** | **작업 + 코드 지도** | **지도 위의 발자취, 승인 전 영향 반경, 기억 지도** |

다른 도구들도 대화와 Diff는 보여준다. Lantern만 할 수 있는 것은 로컬 맥락 엔진이 이미 알고 있는 **코드 구조(심볼·참조·함께 바뀐 이력·프로젝트 기억)** 위에 에이전트의 행동을 겹쳐 보여주는 것이다.

## 2. 구조

```
┌────────────┬──────────────────────────────┬───────────────┐
│ 작업        │ [편집기 | 지도]  가운데 캔버스  │ 작업 대화       │
│ ● 로그인수정 │                              │ 발자취 요약      │
│   승인 대기  │     ○──○        ◉ 수정한 곳   │ 승인 카드       │
│ ○ 테스트추가 │     │  ◉──○                  │  └ 영향 반경     │
│ ────────── │     ○                         │               │
│ 기억 · 파일  │                              │               │
└────────────┴──────────────────────────────┴───────────────┘
```

- **왼쪽은 작업이 먼저다.** 활동 표시줄 맨 위가 작업·기억이고, 파일 탐색기·검색·소스 제어는 그 아래 묶음이다.
- **가운데는 편집기와 지도를 오간다.** 프로젝트를 열면 지도부터 보인다. 파일을 열면 편집기로 돌아간다.
- **편집 조작과 단축키는 그대로다.** 구조가 달라도 손에 익은 동작(Ctrl+P, Ctrl+S, 탭, 명령 팔레트)은 VS Code와 같다.

## 3. 기능

### 코드 지식그래프
- 파일이 150개 이하면 파일 단위, 넘으면 폴더(모듈) 단위로 시작한다. 두 번 누르면 폴더 → 파일 → 심볼로 내려간다.
- 간선: 참조·호출(화살표), 함께 바뀜(청록 점선, git 이력), 기억 연결(점점선).
- 참조는 이름 기반이다. 같은 이름이 4곳 이상 정의된 흔한 이름(get, new 등)은 잡음이라 잇지 않는다.

### 에이전트 발자취
- 작업마다 AI에 보낸 맥락, 에이전트가 읽은 파일, 실제로 바꾼 심볼을 모은다.
- 지도에 겹치면 발자취 밖은 흐려지고, 에이전트가 방금 본 곳에 고리가 번진다.
- 수정 표시는 파일 전체가 아니라 영향 반경이 찾은 "실제로 바뀐 심볼"만 칠한다.

### 변경 영향 반경
- 파일 수정 승인 카드에서, Diff의 바뀌는 줄 → 그 줄을 감싼 가장 안쪽 심볼 → 직접 호출자 → 간접 호출자를 찾는다.
- 함께 바뀌곤 하던 파일, 영향 범위의 테스트, 영향이 닿는 모듈 수로 위험도를 매긴다.
  - 높음: 직접 호출 10개 이상, 다른 모듈 2개 이상, 또는 직접+간접 25개 이상
  - 보통: 직접 호출 3개 이상, 함께 바뀌던 파일 3개 이상, 또는 호출자는 있는데 테스트가 없음
- "지도에서 보기"로 빨강(바뀌는 곳)·주황(직접)·주황 점선(간접)·초록(테스트)을 본다.

### 프로젝트 기억 지도
- `.lantern/memory/<주제>.md`의 목록 줄 하나가 기억 하나다. 에이전트의 `remember` 도구와 기억 보기가 같은 파일을 쓴다.
- 기억 본문에서 심볼 이름과 파일 경로를 찾아 코드와 잇는다. 기억 보기에서는 칩으로, 지도에서는 마름모와 점점선으로 보인다.
- 비밀처럼 보이는 값은 기억 본문에서도 가린다.

### 작업 저장
- 작업의 화면 기록과 모델 대화를 **앱 데이터 폴더**(`tasks/<프로젝트 키>/`)에 저장한다. 대화에는 코드와 민감한 내용이 섞일 수 있어 프로젝트 폴더(= git 저장소)에는 두지 않는다.
- 다시 켜면 기록을 재생해 대화·발자취·승인 결과·되돌리기 버튼까지 되살린다. 실행 중에 닫힌 작업은 "중단됨"으로 표시되고, 메시지를 보내면 저장된 모델 대화에 이어서 한다.
- 되돌리기 원본도 디스크(`checkpoints/`, 14일 보관)에 있어 다시 켠 뒤에도 되돌릴 수 있다.
- 되돌리기 전에 "이 작업 뒤로 다른 곳에서 바뀐 파일"을 지문으로 확인해, 있으면 한 번 더 묻는다 (다른 작업이나 사용자의 변경을 조용히 덮어쓰지 않게).
- 프로젝트마다 최근 60개까지 보관한다. 창을 닫을 때 밀린 저장을 끝낸다.

### 작업 격리 (git worktree)
- 작업을 시작할 때 "격리"를 고르면 `lantern/<id>` 브랜치의 작업 공간(앱 데이터 폴더)에서 에이전트가 읽고 쓰고 명령을 실행한다. 시작점은 지금 프로젝트 상태 그대로다 (커밋하지 않은 변경, 추적하지 않는 파일 포함).
- 끝나면 "격리된 작업 공간에 파일 N개 변경 — 프로젝트는 아직 그대로"와 함께 변경 보기 / 프로젝트에 적용 / 버리기. 적용은 `git apply --check`로 먼저 확인하고, 프로젝트의 같은 곳이 그사이 바뀌었으면 아무것도 바꾸지 않고 알려 준다.
- 격리하지 않은 작업끼리 같은 파일을 고쳤으면 작업 목록에 "겹침 N"을 표시한다.
- 작업을 닫거나 오래된 작업이 정리될 때 작업 공간과 브랜치도 지운다.

### 언어 서버로 영향 반경 확인
- 파일의 언어 서버가 이미 켜져 있으면, 바뀌는 심볼의 참조를 `textDocument/references`로 다시 세어 승인 카드에 "언어 서버로 확인함"을 붙인다 (서버를 새로 띄우지는 않는다).
- 이름이 여러 곳에 정의되어 있으면 언어 서버 결과를 쓰고, 한 곳에만 정의되어 있으면 이름 기준과 합친다. 언어 서버는 열린 파일·설정된 프로젝트만 보는 경우가 있어서다 (검증 중 실제로 tsconfig 없는 TypeScript가 테스트 파일의 호출을 놓쳤다).

## 4. 한계와 다음 단계

| 한계 | 다음 단계 |
|---|---|
| 지도 자체는 이름 기반 참조 (언어 서버 확인은 승인 카드에서만) | 지도 주변 보기에도 언어 서버 참조를 겹치기 |
| 격리 작업의 맥락 조립은 프로젝트 쪽 인덱스를 쓴다 | 작업 공간에서 바뀐 파일은 작업 공간 내용으로 맥락 조립 |
| 격리 작업 적용이 충돌하면 사용자가 직접 옮겨야 함 | 3-way 병합 화면 |
| 영향 반경 위험도 기준은 경험값 | 실제 사용에서 되돌린 작업과 비교해 조정 |
